# 見張りの常駐化 設計案

- 状態: 設計のみ（実装しない）。2026-11-07、Muse 起案。
- 対象: `R:\claude\claude-bridge\muse_monitor.py`（以下「見張り」）。
TrayTools の外で動く独立した Python で、Muse アプリの画面状態の判定、
承認カードのつつき・自動承認（委任条件内）、郵便受けの送受信、
`muse_bridge_status.json` の書き込み、休止の合図への追随を担っている。

## いまの形と問題

- 見張りは Claude のセッションのバックグラウンド作業として起動され、
「Claude を起こす」用件のたびにセッションが終わり、Claude が再起動する。
- 用件のたびに Claude の起動コストと待ち時間がかかる。用件が無い時間帯も、
セッションの都合で見張りの寿命が決まってしまう。
- 見張りの仕事の大半（画面判定・つつき・自動承認・郵便受け・状態ファイル）は
Claude を必要としない。Claude が要るのは「判断が要る用件で起こす」ときだけ。

## ゴール

1. PC 起動（ログオン）で自動起動する。
2. 落ちたら自動で再起動する。ただし暴走する再起動は止めて知らせる。
3. 「起こす用件」では見張りは終了しない。自動承認は Claude 無しで続ける。
4. Claude を起こす部分は、見張りが合図ファイルを書き、Claude 側の軽い
待ち受けがそれを拾う形にする。
5. 常駐プロセス（TrayTools 本体）に UIA を入れない方針を守る。画面判定に
UIA が要るなら、それは見張りのプロセスの中だけに閉じる。

## 選択肢

### A. Windows タスクスケジューラが見張りを所有する

- ログオン時トリガーで `pythonw.exe muse_monitor.py` を起動し、タスクの
「失敗時の再起動」（1分間隔・回数上限）で落下復旧する。
- 長所: OS 標準の仕組みで、TrayTools の再起動（更新が頻繁）に見張りが
巻き込まれない。新しく常駐側に書くコードが最小（登録スクリプトだけ）。
- 短所: 「プロセスは居るがループが固まっている」状態はタスクスケジューラ
では検知できない（後述のハートビートで別途見る）。タスクの登録状態が
PC ごとにぶれやすい。対話セッション必須の設定（後述）を間違えると、
ロック画面で画面判定ができず「状態不明」が続く。

### B. TrayTools が子プロセスとして起動・監視する

- TrayTools 起動時に見張りを子プロセスとして起こし、終了を見て
バックオフつきで起こし直す。環境2・3では起こさない（ブリッジの
環境連動と揃えられる）。状態は既存のブリッジ表示にそのまま出せる。
- 長所: 入口が1つになる。異常時にトレイ通知まで一貫する。
- 短所: TrayTools の再起動のたびに見張りも道連れになる（切り離して
「養子」にする手はあるが、その場合は実質 A と同じで、所有の所在が
曖昧になる）。TrayTools 側にプロセス管理のコードが増える。見張りの
起動に失敗する経路が、常駐本体の起動経路に混ざる。

### C. 両方（所有は A、健康監視は既存の表示）

- 起動と落下復旧はタスクスケジューラが持つ。生きているかの判定は、
既にブリッジがやっている「状態ファイルの last_poll が古ければ
見張りが止まっています」をそのまま使う。TrayTools はプロセスを
一切管理しない。
- 長所: 新規コードが最小。A の「固まり検知できない」弱点は、
既存の鮮度判定がすでにカバーしている。
- 短所: 固まった場合の復旧は人の手（または B の追加）が要る。ただし
固まりは落下より稀で、まずは「気づける」ことが先。

## 共通の部品

### 二重起動の防止

- 見張り自身が名前付きミューテックス（例: `Local\traytools-muse-monitor`）を
起動直後に取る。取れなければ「もう居る」として静かに終わる。
TrayTools 本体の単一起動と同じ作法（`CreateMutexW`。プロセス一覧は
venv スタブの都合で常時2つに見えるので、数で判定しない）。
- 移行期間中は旧来のセッションバックグラウンド起動と併存しうるが、
ミューテックスがあれば二重には動かない。

### 落ちた・固まったの検知と通知

- ハートビートは既存の `muse_bridge_status.json` の `last_poll` を使う
（見張りが毎周期書く。新規の仕組みは足さない）。
- 検知の置き場所はブリッジ（TrayTools）: 鮮度切れで既に
「見張りが止まっています」と出る。これに加えて、鮮度切れが一定時間
（例: 10分）続いたら1回だけ Pushover 等で知らせる案（任意・後段）。
- タスクスケジューラの再起動が短時間に上限へ達したら、タスク側の
最終結果を次回ログオン時に見張りが拾って記録する（任意・後段）。

### 合図ファイル（見張り → Claude の起床依頼）

- 置き場所: `%LOCALAPPDATA%\traytools\muse_wake\` に **1用件1ファイル**
（`wake-<id>.json`）。読み直し→丸ごと書き戻しの競合を避けるため、
1ファイル共有にはしない（bridge_journal がプロセス別ファイルにした
のと同じ理由）。
- 書き込みは一時ファイル＋置き換え（状態ファイルと同じ作法）。
- 中身の例:

```json
{
"id": "wake-20261107-01",
"requested_at": 1760000000.0,
"reason": "mailbox | issue | approval_stuck | unknown_state",
"mailbox_id": "mb-20261107-35",
"note": "80字までの見出し（詳細はチャットか Issue）"
}
```

- Claude 側の待ち受けは、用件フォルダを数秒間隔で覗き、新しい id を
見たら処理し、処理済みは `done\` へ移す（消すのではない。記録として
残し、保持は14日程度で掃除）。見張りは ack を待たない（書きっぱなし）。
未処理が滞留したら、それ自体が「Claude 側が止まっている」兆候として
ブリッジの郵便受けカード相当で見えるようにする（任意・後段）。
- 郵便受け（制御チャネル）の規約は変えない。これは PC 内の起床専用で、
トークン類は入れない。

### 自動承認まわり（変えないもの）

- 自動承認の委任条件（repo が tray-tools、ブランチ main か muse/*、
ファイル範囲）・の合図・休止の合図ファイルへの
追随は、現行のまま移す。常駐化は「誰がプロセスを所有するか」と
「起こし方」だけの話で、承認の判断経路には触らない。
- 休止の合図が見張りにとっての kill switch である点も現行どおり
（休止中はつつき・自動承認・起床を全部止める）。

## 移行の手順（段階案）

### 第1段階（最小）: 所有だけをタスクスケジューラへ

1. 見張りに名前付きミューテックスの取得を足す（取れなければ終了）。
2. 見張りの「起こす用件で終了する」動きを、合図ファイルの書き込みに
切り替える。切替フラグ（設定ファイルの1キー）で旧動作にも戻せる
ようにしておく。Claude 側の待ち受けが未整備の間は、合図ファイルは
「書かれるだけ」で、起床は従来どおり（フラグで併用期間を持つ）。
3. `schtasks` 登録スクリプト（ログオン時起動・対話セッションのみ・
失敗時1分間隔で最大3回再起動・バッテリー条件オフ）を用意し、
自宅PCで登録する。
4. 1週間、セッション側からの起動を止めて様子を見る。見るのは
muse_monitor.log の起動回数（想定は「ログオン＋落下時のみ」）と、
ブリッジの「見張りが止まっています」の出方。

### 第2段階: Claude 側の待ち受けを合図ファイルへ

1. Claude 側の軽い待ち受け（既存の watcher のポーリングに相乗りさせる
か、小さな専用ループ）を用意し、合図ファイルを拾って Claude を起こす。
2. 安定したら第1段階の切替フラグを新動作に固定し、旧動作を外す。

### 第3段階（任意）: 通知と復旧の強化

- 鮮度切れの継続を Pushover で1回知らせる。
- 固まり（プロセスは居るが last_poll が進まない）の自動復旧が要ると
分かったら、その時点で B（TrayTools による監視つき再起動）を
追加で検討する。最初からは入れない。

## リスク

- **対話セッションの要否**: 承認カードの検出とつつきは対話画面が前提。
タスクは「ユーザーがログオンしているときのみ実行」にする。ロック中は
画面判定が「不明」に倒れることがありうるので、その間の自動承認は
現行どおり「判定できなければ押さない」を守る。
- **venv の作り直し**: タスクが指す pythonw.exe のパスは venv の場所に
依存する。venv を作り直したらタスクの再登録が要る（登録スクリプトを
setup の流れに寄せると漏れにくい）。
- **無人時間の伸長**: 常駐化で「PC の前に誰も居ない時間」にも自動承認が
動き続ける。委任条件は変えないが、気になる場合は「最終操作から
○時間を超えたら自動承認だけ止める」ような上限を別途検討する。
少なくとも休止の合図が常時効くことは実機で確認済みの手順にしておく。
- **二重の所有者**: 移行中にタスクとセッション起動が両方生きていると、
ミューテックスで二重実行は防げるが、「どちらが正か」が曖昧になる。
第1段階の完了時点でセッション側の自動起動は止める。
- **合図ファイルの滞留**: Claude 側が長く止まると wake ファイルが溜まる。
id ごとに1ファイルなので実害は小さいが、保持期間と掃除を決めておく。

## 結論（おすすめ）

- **C案（所有はタスクスケジューラ、健康監視は既存のブリッジ表示）を
推す。** TrayTools 本体にプロセス管理と UIA の気配を持ち込まず、
更新で頻繁に再起動する常駐と、止まってはいけない見張りの寿命を
分けられる。固まり検知は既存の鮮度判定で足り、足りないと分かった
場合だけ B の監視を追加すればよい。
- **最小の第1段階は上記の「第1段階」**: ミューテックス＋合図ファイル
への切替（フラグつき）＋タスク登録スクリプト、まで。TrayTools 側の
コード変更はゼロで始められる。
