# 見張りの常駐化 設計の穴探し（第1段階の実装前に）

- 対象: `docs/watcher-resident-design.md` の第1段階（タスクスケジューラ
  MuseBridgeMonitor による所有＋合図ファイル化）を実装する前に
  潰しておきたい失敗しうる点。重要な順に5件。
- 各件: 何が起きるか／なぜ先に決めるべきか／実装前の一手。

## 1. 「失敗時の再起動」は、終了コードが正直なときにしか発動しない

- 何が起きるか: タスクスケジューラの再起動は、タスクの実行が
  「失敗」（0以外の終了コード等）で終わったときだけ働く。見張りの
  メインループが例外を握り潰して0で終わる経路があると、落ちたのに
  再起動されず、誰も気づかないまま止まり続ける。逆に、ミューテックス
  を取れなかった2本目が0で終わるのは正しい（再起動不要）。また
  再起動の回数上限を超えると、次回ログオンまで復活手段がなくなる。
  受け入れ項目2の「約1分で戻る」も、再起動間隔（最小1分）と上限の
  設定値そのものに依存する。
- なぜ先か: 「落ちたら戻る」は常駐化の核で、ここが設定と実装の
  両方にまたがる。後から直すと、タスク定義とコードの両方を
  触ることになる。
- 一手: 終了コードの規約を先に決める（致命時は必ず0以外で終了、
  正常終了はタスクの終了・無効化のときだけ）。再起動は間隔1分・
  上限は十分に大きく（例: 999回）し、上限到達はログに残す。
  「既存のインスタンスが実行中のときは新しいインスタンスを
  開始しない」設定にしておく。

## 2. pythonw には標準出力がなく、死因が証拠なしに消える

- 何が起きるか: `pythonw.exe` はコンソールを持たないので、print や
  未処理例外のトレースバックはどこにも出ない。さらに悪いことに、
  `sys.stdout` が None の環境で出力しようとすると、それ自体が例外に
  なって処理を落とすことがある（エラー処理の中の print が
  とどめになる型）。結果として「黙って死ぬ・ログにも何もない」が
  起きうる。1件目と組み合わさると、再起動もされず証拠もない、
  一番厄介な止まり方になる。
- なぜ先か: 常駐物の observability は後付けが効かない（死んだ回は
  二度と再現しないことが多い）。
- 一手: 診断出力は全部ファイル（`muse_monitor.log`、ローテーション
  あり）へ寄せ、 resident 経路では print を使わない。最上位に
  excepthook を置き、例外をログに書いて0以外で終わる。受け入れでは
  python でなく pythonw で起動して確認する（項目1・2の実施時に
  自然に効く）。

## 3. ミューテックスは「居る」ことしか保証せず、「固まった1本目」が再起動を塞ぐ

- 何が起きるか: 名前付きミューテックス（`Local\…`）は保持プロセスが
  死ねば OS が解放するので、強制終了→再起動は妨げない。しかし
  (a) Python 側でハンドルへの参照を失うと GC で閉じてしまい、
  二重起動がすり抜ける。(b) 1本目が「生きているが固まっている」
  場合、手で起動した2本目は取れずに静かに終わり、利用者は
  「起こしたつもり」になる。(c) `Local\` はログオンセッション
  ごとの名前空間なので、RDP やユーザーの切り替えで別セッション
  から起動すると、セッションごとに1本ずつ動いてしまう。
- なぜ先か: 二重起動防止は第1段階の明示の要件で、(a) は実装の
  一手間で防げる型、(b) は運用手順の書きぶりにまで影響する。
- 一手: ハンドルはモジュール先頭で取り、プロセス終了まで参照を
  持ち続ける。取れなかった側は必ずログに「すでに動いているため
  終了」を残す。「居るのに固まった」の検知はミューテックスでなく
  状態ファイルの鮮度（設計案どおり）に寄せ、手順書にも
  「プロセス数で判断しない」と明記済み（watcher-operations.md）。

## 4. スリープ復帰の瞬間は、時計も画面も信用できない

- 何が起きるか: スリープ中はプロセスが止まり、復帰で時刻が一気に
  進む。`kind_since` 等からの経過計算が跳ねて、承認待ちの警告が
  誤発火したり、逆に古い状態を新鮮と誤認したりする。復帰直後の
  ポーリングが、デスクトップが使えるようになる前に画面判定を
  して誤った状態を書くこともある。タスクスケジューラは
  「プロセスが生きている」ので助けてくれない。
- なぜ先か: 在宅のPCは毎日スリープ復帰する。誤発火が続くと、
  警告そのものが信用されなくなる（ブリッジの存在意義の側の問題）。
- 一手: ポーリング間隔の実測ドリフトが大きい（=眠っていた）周回を
  検出し、その1周は「再同期」として 読み取りと記録だけにし、
  つつき・自動承認・起床を行わない。安い保険なので第1段階に
  入れる。受け入れ項目9はこの確認。

## 5. ロック画面では画面判定が「失敗」ではなく「空」を返しうる

- 何が起きるか: 画面ロック中は対話デスクトップが切り替わり、
  Muse アプリへの UIA 等の読み取りは失敗するか、対象が無い
  結果を返す。怖いのは、失敗がエラーでなく「カードが無い」
  「終わった」といった正規の状態に見える形で返る場合で、
  見張りがターンの終了や承認の解消を誤認する。自動承認は
  「カードを正しく識別できたときだけ押す」が絶対条件。
- なぜ先か: ロック中に押さないのは仕様だが、ロック中を
  「別状態と誤認しない」のは別の要件で、状態の語彙
  （kind に「不明」を含めるか）に触るため、状態ファイルを
  読むブリッジ側との取り決めが要る。
- 一手: 読み取りの失敗・空振りは必ず「不明（unknown）」として
  状態ファイルに書き、idle/done 等へ寄せない。ロック解除後も
  1周は正常に読めるまで承認・つつきを行わない。受け入れ
  項目10はこの確認。
