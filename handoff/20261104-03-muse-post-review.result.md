## 指摘

### 安全確認の抜け

1. **新しいチャットの「準備できた」判定が状態だけで、画面が切り替わった証拠を見ていない**
- 場所：`is_new_chat_empty`（238行）／`check_new_chat_ready`（243行）／`cmd_post` の待ち（592行付近）。
- 入力と起きること：投稿前に表示されていたチャット自体が「作りたてで空」（メッセージのボタン0個・作業中でない・投稿欄が空）だと、`新しいサイドチャット` を Invoke した直後の最初の scan で、まだ画面が切り替わる前でも条件が真になってしまう。そのまま旧チャットの投稿欄に SetValue して送信するので、投稿は「新規に作ったはずのチャット」ではなく元の空チャットへ行き、作っただけの空チャットも残る。
- 直し方の案：Invoke 前の状態（例：投稿欄の要素の RuntimeId、またはチャット名＋子孫の総数など）を覚え、「Invoke 前と違う画面であること」を ready の条件に足す。要素の同一性が取れないなら、Invoke 直後の1回目の scan は無条件に捨てて最低1回は画面変化を待つ形でもよい。

2. **最終確認（scan）と SetValue／Invoke の間に検査と実行の隙間があり、その間に人が打つと上書き・誤送信が起こりうる**
- 場所：`cmd_post` の SetValue（603行）と送信 Invoke（613行）。どちらも直前の poll が返した `refs` の要素を使い、実行の直前にその要素の中身を読み直していない。
- 入力と起きること：poll が「空」「読み戻し一致」と判定した直後に陽太さんが同じ投稿欄へ打ち始めると、SetValue はその書きかけを消し、送信側では混ざった文面を送る可能性がある。隙間は短いが、この道具のいちばんの約束（人の入力を上書きしない）に関わる箇所なので、他の確認が全部 scan 単位で閉じている点と合わせて指摘する。
- 直し方の案：`set_value` の直前に同じ要素を `read_value` して空であることを再確認する。送信 Invoke の直前にも同じ要素を読み直して一致を確認する（scan し直しではなく要素単位の再読なら隙間はほぼ閉じる）。

3. **`check_before_invoke`（265行）だけ busy（『停止』があるか）を見ていない**
- `check_initial` と `check_before_set` は busy を止める理由にしているのに、送信を押す直前の確認には無い。SetValue の待ち（最大4秒）の間に表示中のチャットが作業中になった場合（別経路で生成が始まる等）、読み戻し一致と『送信』1個だけで押してしまう。
- 直し方の案：`check_before_invoke` にも `check_before_set` と同じ busy 確認を足し、テストも1件足す（現行テスト `test_before_invoke` に busy のケースが無い）。

4. **要素の同定が窓全体の Name 完全一致だけなので、別画面の同名要素が単独で現れると誤認しうる**
- 場所：`MUSE_PROFILE`（66〜85行）と `scan`（403行）。投稿欄は Name「メッセージ」の Edit、送信は Name「送信」の Button を窓の子孫ぜんぶから集める。複数あれば個数チェックで止まる作りは良いが、例えばモーダルや別ペインに同名の Edit＋Button が1組だけ出ていて本来の投稿欄が見えない状態だと、個数は1ずつになり、読み戻し一致まで通ってそのボタンを押す可能性がある（実在する画面かは未確認なので確信度は低）。
- 直し方の案：候補要素の祖先（会話ペイン側か）や AutomationId／ClassName の補助条件で投稿欄まわりに寄せる。無理なら、少なくとも実機でダイアログ類を開いた状態を `status` で測っておく。

### 例外時に UI を中途半端な状態で残す経路

5. **SetValue 後に例外が起きると、投稿欄へ書いた文字が戻されずに残る**
- 場所：`cmd_post`（551行〜）。`_restore_input` で空に戻すのは、送信準備の poll が時間切れになった経路（606〜611行）だけ。一般の `except`（636行付近）は理由を記録して返すだけで、復旧を試みない。
- 起きる例：送信ボタンの `invoke` が「InvokePattern が無い」で RuntimeError を投げた場合（押す前なのに文字だけ残る）、poll の上限時の最終 scan（`poll` 452行付近、未取得なら取り直す）が COM 例外を投げた場合。この状態で次に実行すると「投稿欄が空でない」で止まり続け、画面上も書きかけに見える。
- 直し方の案：`except` 側でも「自分が書いた後で、まだ送っていない」ことが分かっている範囲では `_restore_input` を試み、戻せたかを `steps` に残す。送信 Invoke の後に来た例外は「送れたか不明」として区別する（`posted_at` を Invoke の直前に立てる等）。

6. **新しいチャット作成の途中で止まると、UI 側の副作用（開いた一覧・作った空チャット）が残り、再実行のたびに増える**
- 場所：`cmd_post`（580〜597行）。一覧を開いた後に『新しいサイドチャット』が出ない／2個ある、作った後に ready にならない、といった中止経路は、そのまま返す。一覧は開いたまま、作った空のサイドチャットも残るが、結果の `reason` にはその残存が書かれず、`steps` を読まないと分からない。再実行するとまた新しい空チャットが1つ増える。
- 直し方の案：せめて中止理由か `steps` に「一覧を開いたまま」「空のサイドチャットが1つ残っている」を明示する。閉じる／消す復旧は UIA で安全にできる確証がないので、自動復旧より先に明示が現実的。

### wait の判定の誤り

7. **`wait` は `--path` を付けないとブランチが「作られただけ」で成功を返す**
- 場所：`cmd_wait`（641行〜）とファイル冒頭の使い方（8行）。コード内コメント（662〜665行）でも認めているとおり、Muse はブランチを先に作る運用なので、出現＝未完了である。にもかかわらず冒頭の使用例は `--path` 無しで、呼ぶ側がそのまま真似ると作業完了と誤判定する。今回の試運転のように Claude が事前にブランチを作る運用では、出現すら作業開始前から真になっている。
- 直し方の案：結果ファイルのパスを必須にするか、`--path` 無しの成功は `"ok": true` ではなく「ブランチ出現のみ」を表す別の状態（例：`appeared: true, ok: false`）で返す。使用例も `--path` 付きに直す。

8. **`wait` の実待ち時間が `--timeout` を最大で約3分超えうる**
- 場所：`cmd_wait` のループ（653〜694行）。1周で `ls-remote`・`fetch`・`cat-file` の最大3本を、それぞれ `GIT_TIMEOUT = 60` 秒で直列に呼ぶ。`--timeout` の判定は各周の終わりにしかないので、例えば `--timeout 10` でも git が応答しなければ60秒（fetch まで進めばさらに）返らない。
- 直し方の案：各 subprocess の timeout を「全体の残り時間と GIT_TIMEOUT の小さい方」にする。少なくとも上限超えがありうることを出力（`waited_sec` は実績を返すので、呼ぶ側が前提にしないよう）に明記する。

9. **`wait --path` が返す `sha` は、パスの有無を確かめたコミットと別になりうる**
- 場所：`cmd_wait`（656〜683行）。返す `sha` は `ls-remote` で取ったもので、パスの有無はその直後の `fetch` で得た先端で確かめている。2つの間に push があると、「その sha に結果ファイルがある」という保証がない sha を成功として返す。窓は1周の中だけなので確信度は低。
- 直し方の案：fetch 後に `rev-parse refs/remotes/origin/<branch>` で取り直した sha を返し、それで `cat-file` も確かめる。

10. **送信後の「空に戻った」判定（618行）は、表示が別チャットに切り替わっても真になる**
- 判定は「投稿欄が1個あり空であること」だけで、その投稿欄が送信したチャットのものかは見ていない。CLEAR 待ち（最大6秒）の間に表示が切り替わると、未送信でも成功扱いになりうる。人のクリックが前提なので確信度は低。
- 直し方の案：判定にチャット名（`chat_title` が送信先のものと矛盾しないこと）か、メッセージのボタンが増えたことを併せて使う。

### テストの抜け

11. **純関数テストという触れ込みでも、import の時点で UIA 依存に縛られていて、この VM（Linux）ではテストが起動すらしない**
- `muse_post.py` は冒頭（43〜56行）で `comtypes` と `copilot_loop` を無条件に import する。こちらで `import muse_post` を試すと `ModuleNotFoundError: No module named 'comtypes'` で止まることを確認した。テストファイル冒頭の「Muse アプリが無くても通る。UIA には触らない」は Windows＋venv 前提でのみ成り立つ。
- 直し方の案：判断ロジック（純関数の集まっている節）を UIA import の無いモジュールへ分けるか、UIA 側の import を遅延させる。そうすれば純関数テストが CI の別 OS でも回せる。

12. **`cmd_post` の進行そのもの（順序・中止・復旧）にテストが無い**
- 現行テストは純関数のみで、`Muse` を差し替えられない（`cmd_post` がグローバルの `Muse()` を直接作る）ため、以下が丸ごと未検証：dry-run が何も Invoke しないこと、poll 時間切れで `_restore_input` が呼ばれること、例外時に文字が残る／残らないこと、一覧→新規作成の順序、`_dry_run_plan` の分岐、`_restore_input` の「一致したときだけ消す」判定、`read_message` のファイル読み（BOM・末尾改行・読めないとき終了コード2）。
- 直し方の案：`cmd_post` が使う Muse オブジェクトを差し替え可能にし（引数か小さなファクトリ）、偽の scan／invoke で進行だけを確かめるテストを足す。

13. **`cmd_wait` は `parse_ls_remote` と `redact` しかテストがなく、待ちの本体が未検証**
- 未検証の例：「ブランチはあるが `--path` のファイルが無い間は待ち続ける」「fetch 失敗時に `last_error` を残して次周へ回る」「timeout 時に `last_error` 付きで返る」「git が遅いときの実待ち時間」。一時リポジトリ＋偽の git（PATH 先頭に置くスクリプト）で UIA 無しに確かめられる範囲。
- あわせて、`redact` は URL と `git@` 形式しかケースが無く、空白で区切られた単体のトークン文字列などは伏せられない点も未確認のまま（現状の正規表現は `://` か `@host:` を含む形だけを対象にしている）。
