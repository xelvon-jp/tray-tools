### 1. Claude 案への批評

#### C1. 会議前カウントダウン

- **良い点**：狙う瞬間が鋭い。「会議の5分前」は実際に慌てる瞬間で、通知やリマインダーがノート側（プライマリ）の画面に出て正面の作業画面では見落としやすい、という前提環境への処方として筋が良い。帯が「正面に出続け、消えず、押せば参加できる」形なのも、流れて消える通知との差がはっきりしている。
- **弱い点**：依存が Outlook COM 一点で、**新しい Outlook には COM が無く初日から対象外**になる。職場の移行状況次第で「明日から使える」が崩れる案。旧 Outlook でも、未起動時の起動待ち、予定の読み取り範囲（取りに行く頻度と鮮度）の設計が要る。
- **詰まる点**：COM を常駐プロセスに同居させるのは、このリポジトリの「COM と GC で落ちる」実績と相性が悪い。実装するなら `teams_meeting.py` と同じ子プロセス分離が前提になり、見かけより重い。参加リンクも予定本文の形式が複数あり（本文中の URL、HTML のボタン等）、抽出に外れがある。「リンクが取れないときは帯だけ出す」という段階分けが要る。
- **標準機能との重なり**：Outlook のリマインダーと Teams の会議通知とは重なる。ただしあちらは表示画面とタイミングが統制できないので、「正面・固定・参加まで1クリック」に絞れば独自の価値は残る。重なりの説明はその線で書くべき。

#### C2. 画面共有前のおそうじ

- **良い点**：tray-tools 自身の浮いている窓（付箋は別プロセスで常駐を再起動しても残る、ミラー、カンペ、タスクバーウィジェット）を全部把握しているのは tray-tools の固有の強みで、汎用ツールには真似できない。「準備を一括で」という覚えやすさも良い。共有事故は頻度は低くても1回の被害が大きい種類の困りごと。
- **弱い点**：いちばん見せたくないものは tray-tools の窓とは限らない（ブラウザのタブ、チャット、デスクトップのファイル名）。守備範囲が「自分の窓＋デスクトップアイコン＋通知」までなら、その範囲を機能名と文面で正直に言わないと「おそうじしたから大丈夫」という過信を生んで逆に危ない。
- **詰まる点**：集中モードの切替に公開 API が無いのは致命的で、レジストリ直叩きや設定画面の UIA は脆いので初版の範囲から外すのが現実的。デスクトップアイコンを隠す操作はシェルの状態変更なので、**戻し忘れ対策（タイマーで自動復帰）が初版から要る**。共有の終了は検出できない前提で設計すべき。
- **既存機能との重なり**：プレゼン支援の黒画面／白画面、画面ミラーの静止と場面が近い。差は「覆う」のではなく「自分の窓を片付ける」点で、そこが看板になる。

#### C3. 今日の時間の使い方（作業ログ）

- **良い点**：需要（日報の材料）は本物。「アプリ名だけ」に絞る割り切りは、記録への心理的・規程的な抵抗を下げる方向として一理ある。夕方に集計で出す使い方も合っている。
- **弱い点**：拙案 M4 とほぼ同じ発想で、詳細設計は M4 の方が進んでいる（後述の統合で M4 に一本化するのが妥当）。ただし逆方向の差もあって、アプリ名だけでは「会議アプリに2時間」で日報には粗く、結局思い出し直しになる。タイトルまで取る M4 との差は「精度 vs 規程面の軽さ」のトレードオフとして明記する価値がある。集計の見せ方も、円グラフより帯グラフや一覧の方が時間の内訳は読みやすいと思う。
- **詰まる点**：M4 と同じく、記録すること自体への職場の決まりの確認が前提。

#### C4. パス変換コピー

- **良い点**：小さいのに毎日効く可能性が高い。「ドライブ文字のパスを送って相手が開けない」は実在の摩擦で、変換の種類（UNC／親フォルダだけ／引用符付き／file: リンク）の列挙も具体的。実装規模「小」の見立ても概ね妥当。
- **弱い点・詰まる点**：
  - 本体は変換より**入口**。エクスプローラーで選んだものを Shell COM で拾う方法はあるが、前面のエクスプローラーの特定、複数窓、デスクトップ上の選択などの境界が多い。入口の代替案として、既存の `Ctrl+Alt+V` のピッカー（クリップボードにパス文字列が入っていたら変換候補を先頭に出す）や、あっふのパス系メニューの延長も検討に値する。
  - UNC 化はネットワークドライブの接続情報が取れる場合だけ。ローカルドライブのパスはそもそも相手から見えないので、「変換できないものは変換できないと出す」正直さが要る。
  - `file:` リンクは Teams やメール側のセキュリティで開けないことが多い。出しても使えない場面があるので、形式の候補に入れる前に実地の確認が要る。
  - OneDrive／SharePoint の URL は各アプリ標準の「リンクをコピー」と重なりが大きく、COM で安定して取れるかも不明。ここは標準機能に任せるのが無難。
- **既存機能との重なり**：あっふにはパスをコピーする機能が既にある。差は「変換の種類」と「エクスプローラー前提」で、そこを明確にすれば共存できる。

#### C5. Copilot 定型プロンプト差し込み

- **良い点**：定型文ピッカーと Copilot まわりの既存資産の再利用で小さく作る狙いは良い。「送信は人が押す」という線引きは、このリポジトリの安全方針（キー送信を入れない）とも合っている。M365 Copilot を日常で使う前提では頻度も高い。
- **弱い点・詰まる点**：
  - 最大の詰まりは Claude 自身も挙げた「選択中の文章の取り方」。コピーを人に頼むと手順が増えて定型文の速さが死に、自動でコピー操作を送るのは入力の自動生成で EDR・規程面のリスクとフォーカス事故の危険がある。クリップボード経由にするなら、既存の書式落としが持つ「整形前の退避（元に戻す）」と組み合わせる設計が要る。
  - UIA で入力欄へ**書く**のは、状態を**読む**監視系の知見とは別物。M365 Copilot の UI 更新で壊れやすい前提で、壊れたときの逃げ道（クリップボードに包んだ文を載せて終わり、貼り付けは人）も初版から用意すべき。それなら実装も小さくなる。
  - 包んだ結果のプレビューが無いと、違う文章を包んだ事故に気づけない。定型文の「コピーされる姿が見える」流儀は踏襲すべき。
- **標準機能との重なり**：Office アプリ内の Copilot には選択文に対する操作が組み込まれつつある。差別化は「どのアプリで選んだ文章でも、自分の定型文フォルダの型で包める」という横断性に絞るのがよい。

### 2. Claude の批評への応答

- **M1 窓レスキュー（頻度の問い）**：**頻度については同意し、第1回の主張を修正する**。在宅中心ではドッキングの抜き差しは毎日ではなく、Windows 11 がモニタを取り外したときに多くの窓を自動で寄せるのも事実。M1 の売りは頻度ではなく「起きると作業が完全に止まる度合いと安全さ」だった、と位置づけ直す。そのうえで、自動で寄せてもなお残る場面はある：(1) 最小化されていた窓や、再接続で「元のモニタに戻る」動きをした結果タイトルバーが画面外に残る古いアプリのダイアログ・子窓（モーダルだと作業が止まる）、(2) 解像度の違う RDP セッションを切ったあと（在宅勤務こそ起きる）、(3) 会議室のディスプレイに一度繋いだあと、(4) 前回位置を復元するアプリが起動直後から見えない場合。`Win+Shift+矢印` への回答：あれは「対象の窓が特定できて、アクティブ化できる」場合の解法で、画面外のモーダル等では対象の特定自体が難しく、子窓には効かないこともある。M1 の価値は「特定せず全部まとめて救出し、元に戻せる」点。ただし点数の「毎日効く度」は下げる（第5節）。
- **M2 会議前チェック**：**同意**。Teams 標準のデバイス設定・テスト通話との重なりの説明が要るのはそのとおり。補足すると、テスト通話は設定画面の奥にあり「会議に入る直前」には使われにくく、M2 の勝ち筋は速さと「会議に入らずに終わること」。**C1 の帯から M2 へ進める一体化にも賛成**（統合の表に反映）。ただし C1 が Outlook COM 依存で倒れると M2 まで道連れになるので、M2 はトレイメニューの単独入口を必ず残すことが条件。
- **M3 さっきのファイル**：**同意、2点とも取り入れる**。OneDrive の既知フォルダー移動は前提として明記すべきだった（対象フォルダは固定パスではなく、Known Folder の実体パスで解決する）。Outlook で開いた添付の一時フォルダ（`INetCache\Content.Outlook`）を対象に足す提案も良い。「保存場所を選ばずに開いたファイル」こそ M3 の看板場面に合う。注意点として、そのパスは Outlook の版やプロファイルで変わること、中身は「開いただけの一時コピー」で掃除されうることを、案の側に書いておく。
- **M4 きょうの足跡**：**同意**。C3 と統合して M4 側を残す、規程上グレーになりうる点は最終的に陽太さんの判断を要する事項として明記する、の2点ともそのとおり。C3 から取り入れる点として「アプリ名だけの軽量モード」は良い落とし所で、統合案では**アプリ名のみを既定、窓タイトルは明示的にオンにしたときだけ**に後退させるのがよいと思う（第1回の自分の案からの変更）。
- **M5 改行をほぐす**：**同意**。日本語の行は空白を入れずに繋ぎ、英語の行は空白1つを入れる区別が要る。判定は前行の末尾と次行の先頭の文字種で行い、混在文では前行末尾の文字種を優先する、くらいまで第4回の仕様で具体化したい。「繋ぎ足りない側に倒す」方針は維持。

### 4. 追加の案（M6）

#### M6. IME・Caps の見張り（タスクバーウィジェットの延長）

- **どんな困りごとを解くか**：日本語で打つつもりが半角英数だった、その逆だった、Caps Lock が入っていてパスワードを打ち間違えた、といった入力モードの取り違えは、1回は数秒でも日に何度も起きる。タスクバーの言語表示はノート側（プライマリ）にしかなく、正面の作業画面では見えない。
- **使い方**：タスクバーウィジェットの時計の脇に、今の IME 状態（あ／A）と Caps Lock の有無を小さく出すだけ。見るだけで、操作はしない。ウィジェットが時計のふりをしている間も、モードが変わったときだけ一瞬出す、といった出し方は仕様の回の検討事項。
- **既存機能との関係**：タスクバーウィジェット（セカンダリにトレイの代わりを置く）の延長。あれの存在理由「大事な表示は正面に出す」と同じ線で、音声アイコンの状態表示に並ぶもの。IME 状態そのものを出す機能は既存に無い。
- **実装の見込み**：**小**。前面スレッドのキーボードレイアウトと IME の変換モード（IMM32 の取得系 API）、`VK_CAPITAL` の状態を、ウィジェットの既存のポーリング（最前面維持の 500ms 周期など）に相乗りして読むだけ。入力の自動生成はしない。詰まりそうな点：アプリごとに IME 状態の取得可否が違う（取得できないときは「不明」として出す）、パスワード欄ではモード表示自体が要らない場面の扱い。
- **「明日から使える」度**：**中**。ウィジェットを有効にしていることが前提（有効化はメニューの1クリック）。使っている人には初日から効く。
