# 連携ステージまわり コードレビュー(Muse・読み取りのみ)

- 対象: `chara_sprites.py` / `coop_view.py` / `coop_stage.py` / `claude_progress.py`
  (coop・_muse・タイマー・保存まわり)/ `muse_bridge_status.py` /
  `hooks/claude_hook.py`(pretool と phase)/ 関連テスト
- 基準: main `62f3adb`(2026-11-07)を読んで判断。PC の GUI は試していないので、
  描画の実挙動ではなくコードから分かる範囲の指摘。
- 確信度: 高 = コードからほぼ確実 / 中 = 条件が揃うと起きる / 低 = 可能性の指摘。
- コードは直していない。直し方は方向だけ(1〜2行)。

## 1. 状態ファイルの読みが書き込みとぶつかると、ステージ行が1周期消える

- 場所: `muse_bridge_status.py:66` `read()`、`coop_view.py:56` 冒頭の None 判定
- 起きうること: 見張りが `muse_bridge_status.json` を書いている最中に常駐が読むと
  `json.load` が ValueError → `read()` は None を返し、`coop_view` も None になって
  連携ステージの行が丸ごと消え、次の読み取り(3秒後)で戻る。パネル高さが上下して
  ちらつく。書き込み側が一時ファイル+リネームでない限り起きうる(書き込み側は
  このリポジトリの外なので未確認)。
- 直し方: 読む側で「ファイルはあるのに壊れていたら直前の良いデータを返す」
  (feature_screen 側で保持)、または `read()` で1回だけ短く置いて読み直す。
- 確信度: 中(書き込み側の方式に依存)

## 2. kind があっても kind_since が無いと、承認まわりの警告が永遠に出ない

- 場所: `coop_view.py:74-75`(`kind_elapsed` / `ke`)、`:103-107` の承認判定
- 起きうること: `kind="approval"` で `kind_since` が欠けたファイル(見張りの
  版の過渡期や項目の書き漏れ)では `kind_elapsed=None` → `ke=0.0` に潰れるため、
  「承認カードが見えません」(20秒)も赤の承認待ち(180秒)も発火せず、承認カードは
  `0秒` と出続ける。パネルの存在理由である警告が、静かに無効化される。
- 直し方: `kind_since` が無いときは `since`(無ければ `waiting_since`)へ
  フォールバックして経過を出す。テストに「kind のみ・kind_since 無し」の
  ケースを足す(現状の test_coop_view には無い)。
- 確信度: 中〜高(ロジックは明確。実際に欠けるかは見張りの書き方次第)

## 3. フックの「復活」判定が、遅れて起動した PostToolUse で誤発火しうる

- 場所: `hooks/claude_hook.py:408-411`(`revived`)
- 起きうること: 復活の条件は「状態が DONE/FAIL で、フックのプロセス開始時刻
  (`HOOK_STARTED`)が `ended` より後」。ターンの最後のツールの PostToolUse
  プロセスが OS の都合で遅れて起動すると、Stop が `ended` を書いた後に
  プロセスが始まり、完了済みセッションが RUNNING に戻る。次のターンが来るまで
  「応答中」の幽霊セッションがパネルとトレイに残る。
- 直し方: 復活を認める窓を絞る(例: `HOOK_STARTED - ended` が数秒以内だけ)、
  または transcript の更新時刻など終了後の活動の証拠を併用する。
  test_claude_status に「Stop の後に遅れて tool が来た」ケースが無いので追加を。
- 確信度: 中(仕組みは実在。頻度はプロセス起動の遅れ次第)

## 4. フックの状態書き込みは読み直し→丸ごと書き戻しで、同時実行で項目が落ちうる

- 場所: `hooks/claude_hook.py:351-374`(`update_status`)
- 起きうること: 同一セッションで pretool と posttool のフックが並行に走る
  (並行ツール実行時)と、両方が `claude_status.read` → 自分の項目だけ差し替えて
  `write` するため、後から書いた方に無い項目(計画の更新や phase)が消える。
  表示が一瞬巻き戻る程度のこともあれば、計画が古いまま残ることもある。
- 直し方: 書く直前に再読込して差分だけ当てる範囲を狭める、簡易ロック
  (O_EXCL のロックファイル)を挟む、のどちらか。最低限、競合しうることを
  コメントに残す。
- 確信度: 中(影響は表示寄り)

## 5. paintEvent には例外の受け皿が無い(_tick にはある)

- 場所: `claude_progress.py:370` `paintEvent` / `_paint_row` の coop 経路
- 起きうること: `_tick` は例外を握って常駐を守っているが、`paintEvent` は
  無防備。入力は他プロセスが書く JSON で、`coop_view` / `coop_stage` の
  どこかで想定外の型に当たると、例外が Qt のイベントループへ出る。
  PySide6 では描画中の例外は常駐の異常終了につながりうる。
- 直し方: `paintEvent` の行ループを `_tick` と同じ try/except で囲む
  (落とす行はその回だけ描かない)。
- 確信度: 中(現行の coop_view は型ガードが厚く、今すぐ落ちる箇所は見当たらない。保険の指摘)

## 6. 連携ステージ表示中は 80ms ごとにパネル全体を再描画し続ける

- 場所: `claude_progress.py:106`(`ANIMATION_MS`)、`:299` `_tick` のタイマー開始条件
- 起きうること: coop 行がある間タイマーが常時回り、`paintEvent` は全行を
  描き直す(文字の計測・省略・グラデーション生成を含む)。他の窓に隠れている
  間も止まらない。常駐の常時 CPU としては小さくない。また chara_sprites の
  周期(220ms / 300ms のコマ送り)が 80ms の倍数でなく、Muse の足踏みが
  160/240ms の不揃いな間隔になる。
- 直し方: 再描画は coop 行の矩形だけ `update(rect)` に絞る。周期は
  80 の倍数(240ms)に寄せるとコマが揃う。
- 確信度: 高(再描画範囲はコードから確実)/ 中(足踏みの不揃いが目立つか)

## 7. 負の秒数の扱いが場所によって不揃い

- 場所: `coop_view.py:151-152`(`last_approval_sec`)、`muse_bridge_status.py:170`
  と `panel_view` の `poll_sec`
- 起きうること: `_cards` は `last_approval_sec` をそのまま `f"{…:.1f}秒"` に
  するので、壊れた/手編集のファイルで負値が来ると「-1.2秒」と出る
  (`last_mail_at` 側は `0 <=` で守られているのと対照的)。同じく `poll_sec` が
  負だと describe に「-5秒毎」と出て、panel_view のバーの割合も狂う。
- 直し方: `_num` の利用側でなく入口で、秒数系は負なら None か 0 に寄せる
  (approval_sec は `max(0.0, …)`、poll_sec は `> 0` のときだけ使う)。
- 確信度: 中(通常運用では出ない。外から来る JSON への堅さの話)

## 8. rows_to_show の first_seen_done が掃除されず、キーが衝突しうる

- 場所: `claude_progress.py:146-168`(`rows_to_show`)
- 起きうること: 終わったセッションの「最初に見た時刻」は、セッションが
  一覧から消えた(DONE_TTL 切れ)後も辞書に残り続け、常駐が長いほど少しずつ
  増える。`session_id` も `_path` も無い entry は全部キー `None` を共有し、
  別セッションの折りたたみ時刻が混ざる。ID が再利用されると、終わった直後の
  行が即座に折りたたまれることもある。
- 直し方: 呼び出しのたびに、今の一覧に無いキーを辞書から落とす。
  キーが無い entry は控えを作らない。
- 確信度: 中(増え方は緩やか。None 衝突は entry の作りに依存)

## 9. coop_stage の大きさコメントが古い(日本語コメントの誤り)

- 場所: `coop_stage.py:19`
- 起きうること: コメントは「Muse は 60x50」と言うが、実際の描画は
  次行のとおり `MUSE_CELL=4` で 13x15 → 52x60。次の編集者がこのコメントを
  信じると、配置(足元合わせ・名札位置)の計算を誤る。
- 直し方: 19行目のコメントから Muse の寸法を落とし、20行目の注記に一本化する。
- 確信度: 高(単純な不一致)
